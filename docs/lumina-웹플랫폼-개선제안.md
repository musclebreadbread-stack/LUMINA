# LUMINA 웹 플랫폼 개선 제안

## 1. 종합 판정

현재 LUMINA는 여러 분석 방법의 콘텐츠·근거·한계 고지가 잘 갖춰져 있고, 타로·수비학·심리 평가·운세·궁합은 실제 결과 화면까지 동작했다. 그러나 사주와 점성술의 대표 결과가 운영 환경에서 디코딩되지 않아 전체 플랫폼 기준으로는 **수정 후 재검증이 필요한 상태**다.

가장 먼저 처리할 항목은 결과 파이프라인 복구, URL 개인정보 정책 정합성, 인지능력의 문항 수·IQ 표현 정리다. 그 다음에 긴 설문과 결과 페이지의 사용성, 백분위의 해석 안전성, 반응형·접근성 회귀 테스트를 보강하는 순서가 적절하다.

## 3. 상세 개선안

### 3.1 결과 생성과 디코딩을 하나의 제품 계약으로 관리

현재 가장 위험한 구조는 입력 화면이 정상적으로 제출되는데도 결과 화면에서 payload를 읽지 못하는 상황이다. 계산 엔진의 단위 테스트가 통과하더라도 실제 운영 URL 생성, URL 복원, 결과 페이지의 서버·클라이언트 경계가 어긋나면 사용자는 결과를 받을 수 없다.

권장 작업:

1. 방법별 입력 타입, 인코더, 디코더, 결과 페이지를 하나의 명시적인 계약으로 문서화한다.
2. 프로덕션 URL에서 사주·점성술·궁합을 각각 최소 3개 입력 조합으로 제출한다.
3. 제출 후 다음 항목을 자동 검증한다.
   - 최종 URL이 생성되는가
   - 새로고침 후 같은 결과가 복원되는가
   - 핵심 결과 제목이 존재하는가
   - 계산 근거와 한계 고지가 존재하는가
   - 잘못된 URL은 사용자 친화적 오류로 끝나는가
4. 결과 화면의 “읽지 못했습니다”에는 개발자용 로그와 사용자용 복구 동선을 분리해 제공한다.

완료 기준은 “버튼을 눌렀다”가 아니라 “핵심 결과 내용이 표시되고 새로고침·공유 링크에서도 복원된다”로 잡아야 한다.

### 3.2 URL·공유·저장 정책을 실제 데이터 흐름과 일치

현재 서비스는 대부분 서버에 원문 응답을 저장하지 않는 방향을 설명한다. 이는 장점이지만, 브라우저 주소창·기록·스크린샷·메신저·분석 도구·referrer에는 URL이 남을 수 있다. 특히 수비학에서 실제 결과 URL에 이름 query parameter가 노출된 것은 정책 문구와 직접 충돌한다.

권장 작업:

- 결과에 원문 입력값을 넣어야 한다면 짧은 암호화 토큰이나 로컬 전용 결과 키를 사용하고, 링크 복호화 가능 범위와 만료 정책을 명시한다.
- 이름·출생일·출생지·두 사람의 궁합 정보 등 입력별 민감도를 분류한다.
- 링크 복사 버튼을 누르기 전에 “이 링크에 어떤 정보가 포함되는가”를 보여 준다.
- 공유 미리보기와 OG 이미지에 입력값이 나타나지 않는지 검사한다.
- 개인정보처리방침의 “링크에 포함되는 정보”, “서버 로그”, “광고·분석 파트너”, “IndexedDB·localStorage”, “인지능력 파일럿 저장”을 실제 구현과 대조한다.
- /privacy와 /terms에 초안 문구를 남긴 채 공개 운영하지 말고 법률 검토를 완료한다.

### 3.3 인지능력의 성격을 명확히 분리

인지능력 페이지는 임상검사의 대체물이 아니라고 설명하는 점은 좋다. 하지만 같은 흐름에서 이론적 IQ 추정치와 95% 신뢰구간을 강조하면 사용자는 그 숫자를 IQ 점수로 받아들일 수 있다. 또한 홈의 16문항과 상세의 20문항 표기가 달라 신뢰를 떨어뜨린다.

권장 정보 구조:

1. 공개 연습: 저장 없이 형식과 풀이 경험만 제공
2. 탐색 파일럿: 운영 저장 동의, 진행 방식, 연구 참여 선택을 별도 표시
3. 결과: “정답률·문항 수행 탐색 요약”을 기본으로 제공
4. IQ 환산: 승인된 한국 규준과 타당화가 완료되기 전에는 숨기거나, 보조 설명 안에서만 매우 제한적으로 표시

표준 파일럿을 유지한다면 시작 전에 다음을 명시해야 한다.

- 운영 저장 동의와 연구 참여 동의의 차이
- 저장되는 데이터 항목과 보존 기간
- 중도 철회·삭제 방법
- 연구 참여를 거부해도 가능한 대체 경로
- 현재 결과가 규준 점수가 아닌 이론적 근사라는 사실

### 3.4 백분위와 불확실성의 해석 안전성 강화

Big Five 결과는 모두 30/50인데 요인별 백분위가 8~56으로 달랐고, EQ의 일괄 3점 결과는 백분위 2로 표시됐다. 수학적으로는 참고 표본·변환 방식으로 설명할 수 있지만, 사용자 경험에서는 “보통 응답을 했는데 능력이 매우 낮다”는 식의 오해가 생긴다.

권장 표시:

- 1순위: 원점수와 평균 응답
- 2순위: 측정오차와 신뢰구간
- 3순위: 참고 표본 기반 백분위
- 백분위 옆 고정 라벨: “한국 규준 아님”, “외국 참고표본”, “정규분포 추정치” 등 방법별 정확한 표현
- 같은 번호로 응답한 문항 비율, 응답 범위, 너무 빠른 완료 여부 등 응답 품질 신호
- 품질 신호가 낮으면 해석 문장을 낮은 강도로 바꾸고 “추가 응답 후 재검사”를 안내

사용자는 T 점수나 백분위의 의미를 바로 알기 어렵다. 점수 카드를 클릭하면 원점수·참고 표본·측정오차를 한 화면에서 보여 주는 구조가 적절하다.

### 3.5 설문 작성 경험을 분할하고 복귀 가능하게 개선

50문항 Big Five, 36문항 애착, 33문항 EQ, 27문항 SD3는 모두 직접 실행할 수 있었지만, 문항 수가 많고 한 화면에서 세로로 길게 이어지는 구조다.

권장 작업:

- 5~10문항 단위로 페이지를 나눈다.
- 상단에 전체 진행률과 현재 영역을 표시한다.
- 이전·다음과 미응답 위치 이동을 제공한다.
- 브라우저에 임시 저장할지 시작 전에 선택하게 한다.
- 민감 문항에는 “답하기 어렵다” 또는 “해당 없음”을 제공하되, 그 응답이 점수에 어떻게 반영되는지 표시한다.
- 모바일에서는 라디오 선택 영역을 충분히 크게 만들고 한 화면에 한 문항 또는 소수 문항만 보여 준다.
- 마지막 제출 전에 응답 누락·동일 응답 과다·너무 짧은 소요 시간에 대한 안내를 보여 준다.

### 3.6 결과 페이지를 요약 우선으로 재구성

현재 결과 페이지는 근거·방법론·세부 문장까지 충실하지만, 사용자가 첫 화면에서 “무엇을 얻었는가”를 찾기 어렵다.

추천 순서:

1. 결과 한 줄 요약
2. 핵심 지표 2~5개
3. 해석 시 주의할 점
4. 오늘 또는 일주일 동안 해 볼 행동
5. 계산 근거
6. 신뢰도·규준·역채점·문헌

켈틱 크로스·궁합 관계 표·Big Five 세부 결과는 요약 카드와 세부 아코디언을 조합한다. 표는 모바일에서 카드형 행으로 바꾸고, 용어 설명은 본문을 가리지 않는 툴팁으로 제공한다.

여러 결과를 확인한 뒤 통합 리포트에서 완료 결과 0과 브라우저 저장소 사용 불가 안내가 표시된 것도 점검해야 한다. 이 현상이 일반 브라우저에서도 재현되면 결과 완료 이벤트가 파생 요약 저장소로 전달되지 않는 문제다. 자동화 브라우저의 IndexedDB 제한일 수 있으므로 정상 사용자 브라우저와 새 세션에서 별도로 확인한다.

### 3.7 MBTI와 비공식 확장 축의 정보 구조 정리

MBTI 페이지는 Big Five 기반 참고 해석이라는 고지가 좋고, 경계값에서 물음표를 사용해 확정을 피한다. 그러나 물음표 코드가 오류처럼 보이고, 공식 MBTI의 4축과 LUMINA의 AT·VW 확장 축이 한 이름 아래 섞인다.

권장 표시:

- 제목: “Big Five에서 파생한 MBTI 스타일 참고 요약”
- 공식 4축: E/I, S/N, T/F, J/P
- 보조 축: 정체성·정서 표현 등 LUMINA 실험 축
- 경계값: 코드 대신 “경계에 가까워 방향을 확정하지 않음”
- 확실성: 0%를 단독으로 보여 주기보다 “이번 응답에서 안정적인 유형 방향을 찾지 못함”으로 설명

결과 링크는 실제 사용자 클릭과 키보드 활성화 모두에서 정상 이동하는지 자동화해야 한다.

### 3.8 민감한 심리 결과의 중립적 언어

다크 트라이어드·애착은 결과 라벨이 자아상과 관계에 영향을 줄 수 있다. 현재 고지는 좋은 편이지만 결과 숫자와 기술 용어가 먼저 눈에 들어오면 안전 문구가 뒤로 밀린다.

권장 작업:

- 기술 용어와 사용자-facing 표현을 분리한다.
- 결과 상단에 “진단·도덕적 평가·고정된 성격 판정이 아님”을 고정한다.
- 정신건강 위기나 관계 폭력 등으로 오인될 수 있는 상황의 도움말을 별도로 제공한다.
- 애착 문항은 현재 또는 최근 관계를 기준으로 답하는지 명시한다.
- SD3는 한국어 타당도와 규준의 한계를 백분위 옆에 반복 표시한다.
- 애착 31번·36번처럼 동일 문항이 반복 노출되는 현상을 원문항·역채점·결과 계산에 대해 자동 검사한다.

### 3.9 운세·궁합의 숫자와 해석을 분리

오늘의 운세는 계산 근거와 예측력의 한계를 비교적 명확히 고지한다. 궁합도 고정 점수 대신 관계 신호라고 설명한다. 하지만 조화 3, 조정 8, 천간 비교 4와 같은 숫자는 사용자가 다시 좋고 나쁨 점수로 읽을 수 있다.

권장 작업:

- 숫자 카드 제목을 “계산 관찰값”으로 표시한다.
- “성공 확률·관계의 질·좋고 나쁨을 뜻하지 않음”을 숫자 바로 아래에 둔다.
- 관계 신호를 대화 질문과 연결한다. 예: “서로 다른 기대를 확인할 질문”
- 궁합 링크는 두 사람의 출생 정보가 포함될 수 있으므로 양쪽 공유 동의를 확인한다.
- 오늘의 운세는 현지 날짜와 공개 계산 기준 UTC의 차이를 결과 상단에 표시한다.

### 3.10 접근성·반응형·모션 품질을 독립 회귀 테스트

이번 브라우저 확인에서는 제목·랜드마크·폼 역할·버튼명·이미지 대체 텍스트가 대체로 잘 노출되었다. 다만 이 결과만으로 WCAG 적합성을 확정할 수는 없다.

추가해야 할 자동·수동 검사:

- 375px, 768px, 1440px에서 가로 스크롤·표 잘림·버튼 겹침 확인
- 키보드만으로 홈 → 방법 선택 → 전 문항 → 결과 → 공유까지 이동
- 현재 포커스가 시각적으로 보이고, 진행률 변화가 보조기술에 전달되는지 확인
- 라디오·탭·아코디언·공유 버튼의 이름과 상태 확인
- reduced-motion에서 카드·배경·3D 효과가 정보 접근을 가리지 않는지 확인
- 대비가 낮은 회색 본문 텍스트와 비활성 버튼 점검
- 이미지가 실패해도 대체 텍스트와 핵심 결과가 남는지 확인
- 결과 페이지 인쇄·PDF에서 공유 버튼이 숨고 본문이 정상 출력되는지 확인

### 3.11 기술 부채와 운영 모니터링

브라우저 콘솔에서 Three.js의 THREE.Clock deprecated 경고가 여러 페이지에서 반복됐다. 즉시 사용자 기능을 막지는 않지만, 라이브러리 업데이트 때 실제 오류로 바뀔 수 있는 신호다.

권장 작업:

- 사용 중인 Three.js API와 버전을 확인하고 권장 Timer API로 교체한다.
- 주요 경로 E2E에서 console error·warning을 수집한다.
- 결과 디코더 오류를 Sentry 또는 동등한 오류 추적에 기록하되 URL 원문·생년월일·이름은 마스킹한다.
- 프로덕션 smoke test에 최소한 사주·점성술·타로 한 장·Big Five·궁합을 넣는다.
- 공유 링크를 새 브라우저 세션에서 열었을 때 같은 결과가 재현되는지 검사한다.

## 7. 최종 제안

LUMINA의 차별점은 여러 관점을 한곳에 모으면서도 방법별 신뢰도 계층과 한계를 표시한다는 점이다. 개선 작업의 중심은 기능을 더 추가하는 것이 아니라, 이미 있는 결과가 항상 도착하고, 숫자와 라벨이 과장되게 읽히지 않으며, 어떤 데이터가 URL·브라우저·서버에 남는지 사용자가 이해하게 만드는 것이다.

사주·점성술 결과 복구와 개인정보 정책 정합성을 P0·P1로 먼저 처리한 뒤, 심리 평가의 참고 백분위와 인지능력의 IQ 표현을 정리하면 신뢰성·안전성·사용성이 함께 올라갈 가능성이 높다.
